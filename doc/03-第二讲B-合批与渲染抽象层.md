## 1. 三层结构：谁负责什么

先建立分层地图，否则会在两个文件间迷路：

```
┌────────────────────────────────────────────────────────┐
│ 精灵层（第二讲 A）：sprite.c / renderbuffer.c             │
│   递归精灵树 → 把每个 picture 变成 4 个顶点（已含矩阵/UV）   │
└──────────────────────────┬─────────────────────────────┘
                           │ shader_draw(4顶点, color, add)
┌──────────────────────────▼─────────────────────────────┐
│ 合批层  lib/shader.c（全局单例 RS）                        │
│   · 把四边形攒进 CPU 大数组 vb（最多 1024 个）             │
│   · 记住当前 program / 纹理 / 混合，一变就先 flush         │
│   · 管 16 个 shader program、uniform、材质                │
└──────────────────────────┬─────────────────────────────┘
                           │ render_draw / render_set / render_buffer_update
┌──────────────────────────▼─────────────────────────────┐
│ 渲染抽象层  lib/render/render.c（struct render，RHI）      │
│   · 用 RID 句柄 + 对象池管理 VBO/纹理/shader/RT           │
│   · 编译 GLSL、建 VAO、封装所有 gl* 调用                  │
│   · current/last + changeflag 脏标记，去掉冗余 GL 调用     │
└──────────────────────────┬─────────────────────────────┘
                           │ glDrawElements / glBufferData …
                        OpenGL 驱动 → GPU
```

类比：

- **精灵层**是"把每个包裹填好面单"；
- **shader.c**是"打包员"，把同车的包裹攒满一个集装箱（合批），发现目的地变了就先发一车；
- **render.c**是"车队调度"，手里记着每辆车当前的配置（脏标记），只有配置真变了才去重新设置，还把"怎么码放包裹"（VAO）录成模板复用。

## 2. 一个四边形的完整旅程（逐行主线）

先把主干走一遍，后面再逐节展开。

```
sprite.c: sprite_drawquad()                 叶子矩形
  · 4 个角：本地坐标 × 矩阵 → 世界坐标（/1024 定点）
  · screen_trans() 归一化（screen.c:36）
  · shader_texture(glid, 0)                 选纹理（可能触发 flush）   shader.c:241
  └─ shader_draw(vb[4], color, add)                                   shader.c:284
       └─ renderbuffer_add(&RS->vb, ...)        攒进 CPU 数组          renderbuffer.c:19
            · 拷 4 个顶点，把 uint32 颜色拆成 4 字节
            · object++；满 1024 返回 1
       · 满了 → rs_commit()                                            shader.c:201
            · render_buffer_update(VBO, vb, 4*object)  上传 CPU→GPU    render.c:172
            · renderbuffer_commit → render_draw(TRIANGLE, 0, 6*object) shader.c:195
                 · render_state_commit()  按脏标记下发 GL 状态         render.c:856
                 · glDrawElements(...)     用 IBO 画 object 个矩形     render.c:1022
            · object = 0                   清空，开始攒下一批
```

记住三个"计数器/数组"：

- `RS->vb.vb[]`：CPU 侧大数组，能放 `MAX_COMMBINE = 1024` 个四边形（`renderbuffer.h:7,26`）；
- `RS->vb.object`：当前攒了几个；
- IBO 里每个四边形固定 6 个索引（第一讲的 `0 1 2 / 0 2 3`），所以画 N 个矩形就是 `6*N` 个索引。

## 3. 顶点在内存里长什么样（20 字节）

`renderbuffer.h:9`：

```c
struct vertex_pack { float vx, vy; uint16_t tx, ty; };  // 位置 8B + UV 4B
struct vertex {
    struct vertex_pack vp;   // 12 字节
    uint8_t rgba[4];         // 顶点色 4 字节
    uint8_t add[4];          // 加色(发光) 4 字节
};                         // 合计 20 字节
struct quad { struct vertex p[4]; };  // 一个矩形 = 4 顶点 = 80 字节
```

内存布局（`stride = 20`）：

```
偏移 0         8        12      16      20
┌─────────────┬────────┬───────┬───────┐
│ x,y (2 float)│ u,v u16│ RGBA  │ ADD   │
└─────────────┴────────┴───────┴───────┘
```

启动时把这张"布局表"注册给 GL（`shader.c:104`）：

```c
struct vertex_attrib va[4] = {
  { "position", 0, 2, sizeof(float),    offsetof(vp.vx) }, // 2 个 float
  { "texcoord", 0, 2, sizeof(uint16_t), offsetof(vp.tx) }, // 2 个 u16
  { "color",    0, 4, sizeof(uint8_t),  offsetof(rgba)  }, // 4 个 u8
  { "additive", 0, 4, sizeof(uint8_t),  offsetof(add)   },
};
```

两个省内存/省带宽的细节：

- **UV 用 `uint16_t` 且 normalized**：编译资源时把纹理像素换算成 0~65535，GPU 读取时自动 `/65535` 还原成 0~1，比用两个 float 省一半；
- **颜色用 `uint8_t` 且 normalized**：GPU 自动 `/255`。

`normalized = GL_TRUE` 就是在 `render.c:288` 的 switch 里按分量大小设的（1 字节→u8、2 字节→u16、4 字节→float）。

`renderbuffer_add`（renderbuffer.c:26）把一个 uint32 颜色拆成 4 个字节、4 个顶点各写一份：

```c
q->p[i].rgba[0] = (color >> 16) & 0xff;  // R
q->p[i].rgba[1] = (color >>  8) & 0xff;  // G
q->p[i].rgba[2] = (color      ) & 0xff;  // B
q->p[i].rgba[3] = (color >> 24) & 0xff;  // A（注意 A 在最高字节）
```

## 4. 启动时建好的三样东西：VBO / IBO / 顶点布局

`shader_init()`（shader.c:63）在启动时做一次性准备：

**(1) IBO（索引缓冲，静态、永不变）**——shader.c:90

```c
for (i=0;i<MAX_COMMBINE;i++) {
  idxs[i*6+0]=i*4; idxs[i*6+1]=i*4+1; idxs[i*6+2]=i*4+2;
  idxs[i*6+3]=i*4; idxs[i*6+4]=i*4+2; idxs[i*6+5]=i*4+3;
}
render_buffer_create(INDEXBUFFER, idxs, 6*1024, sizeof(u16)); // GL_STATIC_DRAW
```

**(2) VBO（顶点缓冲，动态、每批重传）**——shader.c:102

```c
render_buffer_create(VERTEXBUFFER, NULL, 4*1024, sizeof(struct vertex)); // 先不填数据
```

每次 flush 用 `render_buffer_update` → `glBufferData(..., GL_DYNAMIC_DRAW)`（render.c:180）重传当前这批顶点。这叫 **buffer orphaning（缓冲孤立）**：每批重新指定一次存储，驱动会直接给块新内存，避免等 GPU 读完旧数据造成 CPU/GPU 同步卡顿。

**(3) 顶点布局 + 绑定到槽位**——shader.c:110

```c
rs->layout = render_register_vertexlayout(...);  // 只是 CPU 侧的属性描述表
render_set(VERTEXLAYOUT, layout);
render_set(INDEXBUFFER, ibo);
render_set(VERTEXBUFFER, vbo);
```

注意：这里的 `layout` 还不是 GL 的 VAO，它只是一份"属性名/分量数/类型/偏移"的描述，真正的 VAO 在 shader 编译时按 program 建立（下一节）。

## 5. VAO：把"顶点怎么解释"录下来

`glVertexAttribPointer`（告诉 GPU"从 VBO 的哪个偏移、按什么类型读 position/uv/color"）是一组较重的状态调用。**VAO（Vertex Array Object）就是把这组设置连同"当前绑的哪个 VBO/IBO"录成一个对象**，以后只需 `glBindVertexArray(vao)` 一键恢复。

这套引擎给**每个 shader program 配一个 VAO**（render.c:83）：

```c
struct shader { GLuint glid; GLuint glvao; RID vbslot[8]; RID ib; ... };
// 创建 program 时：glGenVertexArrays(1, &s->glvao);   render.c:329
```

真正应用在 `apply_va()`（render.c:544）：

```c
glBindVertexArray(s->glvar);              // 恢复这个 program 的 VAO
if (change_vb(R,s)) {                     // VBO 组合和上次不一样吗？
    for 每个属性 i:
        glBindBuffer(GL_ARRAY_BUFFER, 对应vbo);
        glEnableVertexAttribArray(i);
        glVertexAttribPointer(i, size, type, normalized, stride, offset);
}
if (change_ib(R,s)) {                     // IBO 变了吗？
    glBindBuffer(GL_ELEMENT_ARRAY_BUFFER, ibo);
}
```

`change_vb`（render.c:522）就是把"期望的 VBO 槽位数组 `R->vbslot`"和"这个 VAO 里记录的 `s->vbslot`"做 `memcmp`：

- **一样**：VAO 里已经录好了，什么都不用做，省掉一大串 GL 调用；
- **不一样**：重新 bind + `glVertexAttribPointer`，并把新状态记回 VAO。

> 老安卓 / 定义了 `VAO_DISABLE` 时走另一分支（render.c:527）：`change_vb` 恒返回 1，每次绘制都重设——反衬出 VAO 就是为省这件事而存在。

另外 `render_buffer_update` 上传前会 `glBindVertexArray(0)`（render.c:175），避免"往 VBO 写数据"这个动作污染当前 VAO 记录的绑定。

## 6. 脏标记：GL 状态只在真正变化时才下发

render.c 里有两份状态（render.c:94、112）：

```c
struct rstate { target; blend_src/dst; depth; cull; depthmask; scissor; texture[8]; };
struct render {
    uint32_t changeflag;     // 哪些类状态"可能变了"的位掩码
    struct rstate current;   // 上层"想要"的状态
    struct rstate last;      // GL 里"实际"的状态
    ...
};
```

所有 `render_setblend / render_set / render_setdepth …` 都**不直接调 GL**，只做两件事（以 blend 为例，render.c:770）：

```c
R->current.blend_src = src;  R->current.blend_dst = dst;
R->changeflag |= CHANGE_BLEND;     // 记账：混合可能变了
```

真正下发发生在每次 `render_draw` 开头的 `render_state_commit()`（render.c:856）。它逐位检查，且**再比对一次 current 与 last，不同才调 GL**：

```c
if (changeflag & CHANGE_BLEND) {
    if (last.blend != current.blend) { glBlendFunc(...); last = current; }
}
... // texture / target / depth / cull / scissor 同理
changeflag = 0;
```

这是经典的**惰性状态应用（lazy state application）**：

- 上层可以放心地反复"设置"同一个状态，不产生任何 GL 开销；
- 只有一次 draw 真正用到、且状态确实变了，才下发那一条 GL 命令。

`changeflag` 是粗筛（这一类要不要看），`current != last` 是细筛（到底变没变），两层把关。

## 7. 合批的"冻结元组"：到底什么时候必须 flush

第一讲列过"7 种提前 flush 的时机"，这里给你**统一的判据**，不用背。

一次 `glDrawElements` 画出来的所有顶点，共享同一组"绘制状态"。我把这组状态称为一个**冻结元组（batch key）**：

```
{ program（哪对 VS/FS）, 纹理 texture(s), 混合方式 blend,
  uniform 变量值, 渲染目标 target, 裁剪 scissor }
```

已经攒在 `RS->vb` 里、但**还没画出去**的顶点，会按"调用 glDrawElements 那一刻"的状态来画。所以：**只要元组里任何一项即将改变，就必须先 `rs_commit()` 把旧批次封口画掉**，否则旧顶点会错误地用上新状态。

在 shader.c 里能看到每一项变化前都先 commit：

| 变化项 | 代码 | 动作 |
|---|---|---|
| 攒满 1024 个 | `shader_draw` → renderbuffer.c:37 | `rs_commit()` |
| 换纹理 | `shader_texture` shader.c:243 | id 不同先 commit |
| 换 shader | `shader_program` shader.c:267 | program 不同/uniform 脏/带材质先 commit |
| 换混合 | `shader_blend` shader.c:329 | 非默认混合先 commit |
| 改 uniform | `shader_setuniform` shader.c:384 | 先 commit（旧顶点用旧 uniform） |
| 帧末 | `shader_flush` shader.c:314 | commit 剩余不足 1024 的部分 |
| 离屏 blit | `shader_drawbuffer` shader.c:215 | 先 commit 主批次 |

`rs_commit()`（shader.c:201）本身很简单：

```c
if (rb->object == 0) return;        // 空批不画
RS->drawcall++;                     // 统计 draw call
render_buffer_update(VBO, vb, 4*object);   // 上传
render_draw(TRIANGLE, 0, 6*object);        // 画
rb->object = 0;                     // 归零
```

**为什么换纹理最常见地打断合批**：一次 draw 里片元着色器只能采样固定的纹理通道；两张不同的图没法塞进同一次 draw（除非用纹理图集 atlas 或多纹理）。所以美术常把小图拼成图集，就是为了让更多矩形共享同一纹理、合成一批。

## 8. program 与 uniform：编译、定位、缓存、材质

**编译**（render.c:210 起）：`render_shader_create` → `compile()`（glCreateShader/glShaderSource/glCompileShader）→ `link()`。链接前用 `glBindAttribLocation(prog, i, name)`（render.c:284）把属性名固定绑到位置 0/1/2/3（position/texcoord/color/additive），这样所有 program 的顶点布局一致，VAO 才能通用。

**16 个 program 槽**：`shader_load(prog, fs, vs, ...)`（shader.c:147）把 `ejoy2d/shader.lua` 里的 GLSL 字符串编译进槽位（普通精灵=0、离屏=1、文字=2/3、GUI 文字=4/5、灰度=6、纯色=7、遮罩混合=8，9 以后留给用户自定义）。

**uniform 缓存**（避免每帧都 glUniform）：

- `shader_adduniform`（shader.c:396）：`glGetUniformLocation` 拿位置，记录类型和在一块 float 数组 `uniform_value[]` 里的偏移；
- `shader_setuniform`（shader.c:383）：只把新值 memcpy 进缓存，置 `reset_uniform / uniform_change[i]`；
- `apply_uniform`（shader.c:251）：切到该 program 时，**只上传变化过的** uniform（`render_shader_setuniform` → `glUniform*`，render.c:1064）。

**材质 material**（shader.c:420）：把"一组 uniform 值 + 若干纹理"打包成一个可挂在精灵上的对象（`material_apply` shader.c:473）。这样不同精灵用同一套 shader 但参数不同（例如 GUI 文字各自的变换矩阵 `inv_pmv`）；同样带缓存，`p->material == m && !reset` 就直接跳过。

## 9. 真正的着色器源码：为什么顶点着色器只有一个加法

普通精灵的 GLSL 在 `ejoy2d/shader.lua`：

```glsl
// 顶点着色器 sprite_vs (shader.lua:29)
attribute vec4 position; attribute vec2 texcoord;
attribute vec4 color;    attribute vec4 additive;
varying vec2 v_texcoord; varying vec4 v_color, v_additive;
void main() {
    gl_Position = position + vec4(-1.0, 1.0, 0, 0);  // 就这一下
    v_texcoord = texcoord; v_color = color; v_additive = additive;
}
```

**为什么没有投影矩阵？** 因为 CPU 已经把活干完了：

- 矩阵变换（旋转/缩放/平移）在精灵层用定点矩阵算好（第二讲 A）；
- `screen_trans()`（screen.c:36）把坐标乘 `2/宽`、`-2/高`，映射到 x∈[0,2]、y∈[-2,0]；
- VS 只需平移 `(-1,+1)` 就落到 NDC 的 x∈[-1,1]、y∈[-1,1]。

GPU 顶点着色器因此极简，把变换成本留在 CPU、也省掉一个矩阵 uniform。

```glsl
// 片元着色器 sprite_fs (shader.lua:14)
vec4 tmp = texture2D(texture0, v_texcoord);   // 采图
gl_FragColor.xyz = tmp.xyz * v_color.xyz;     // 染色（乘顶点色）
gl_FragColor.w   = tmp.w;
gl_FragColor    *= v_color.w;                 // 顶点透明度
gl_FragColor.xyz += v_additive.xyz * tmp.w;   // 加色发光（只在不透明处）
```

这正好对应顶点里的 `rgba`（乘色/透明度）和 `add`（加色），再由固定混合 `glBlendFunc(ONE, ONE_MINUS_SRC_ALPHA)`（shader.c:88）做标准 alpha 混合。

> 对比：离屏程序 `renderbuffer_vs`（shader.lua:235）就有一个 `uniform vec4 st`，在 VS 里做缩放平移——因为把一张离屏纹理 blit 回屏幕时，变换要由 GPU 做。

## 10. RID 对象池：render 内部怎么管理句柄

第一讲说 RID 是"内存池句柄"，这里看到实现：

- `render_init`（render.c:484）一次性 malloc 整块，切出几个定长对象池：buffer / attrib / target / texture / shader（容量在 shader.c:71 指定，如 max_texture=256、max_shader=16）；
- `array_alloc` 取一个槽，`array_id` 返回 **RID（=数组下标+1 的无符号整数，0 表示空）**，`array_ref` 用 RID 取回结构体；
- 引擎全程只存 RID，从不直接存 `GLuint`。好处：句柄稳定、可校验、上限可控，换后端（GLES / 甚至 D3D）时上层不用改。

## 11. 一帧的完整时序（全部串起来）

```
逻辑帧（Lua update，30Hz）
  改 sprite.frame / 位置 / 文字
        │
绘制帧 drawframe（Lua）
  sprite_draw 递归精灵树（第二讲 A）
    picture 叶子 → sprite_drawquad
      算好 4 顶点（矩阵→screen_trans→NDC 前的 0..2/-2..0）
      shader_texture / shader_program / shader_blend   ┐ 状态一变就
      shader_draw → renderbuffer_add 攒进 RS->vb       ┘ rs_commit
        │  攒满或状态变化 → render_buffer_update + glDrawElements
  label_flush（文字批次）
  shader_flush（shader.c:314）         ← 把最后不足 1024 的余批画掉
        │
GLFW 交换缓冲 swapbuffers → 屏幕呈现
```

两讲合一句话：

> **精灵树 + 定点矩阵负责"算出每个矩形这一帧的顶点/UV/颜色"（第二讲 A）；shader.c 负责"把同状态的矩形攒成一批、在状态变化时封口"（本讲上半）；render.c 负责"用最少的 GL 调用把这批顶点和状态交给 GPU"（本讲下半）；VS/FS 负责"逐顶点补个平移、逐像素贴图染色"（第一讲）。**

## 13. 自测题与答案

**Q1. 一个 `struct vertex` 多少字节？为什么 UV 和颜色不用 float？**

答：20 字节（position 8 + texcoord 4 + rgba 4 + add 4）。UV 用 u16、颜色用 u8 并开 normalized，GPU 自动 /65535、/255，省内存和带宽，精度也够用。

**Q2. VBO、IBO、VAO 各存什么？哪个是静态的、哪个每批重传？**

答：VBO 存顶点（位置/UV/颜色），每批 `glBufferData(DYNAMIC_DRAW)` 重传；IBO 存 `0 1 2 0 2 3` 索引，启动时建一次、STATIC 永不变；VAO 不存顶点数据，只录制"绑哪个 VBO/IBO + 属性指针怎么设"，用于一键恢复。

**Q3. 为什么换一张纹理就会打断合批？**

答：一次 glDrawElements 的片元着色器采样的纹理是固定的；已攒未画的顶点若和新纹理顶点混在一批，会被错误地用新纹理贴图。所以 `shader_texture` 发现纹理 id 变了必须先 `rs_commit()` 封口。纹理图集能减少这种打断。

**Q4. `render_setblend` 调用后立刻发生 GL 调用吗？为什么？**

答：不会。它只写 `current` 并置 `CHANGE_BLEND` 脏标记；真正的 `glBlendFunc` 延迟到 `render_draw → render_state_commit`，且比对 `current != last` 确认真变了才下发。这避免重复设置相同状态。

**Q5. 普通精灵的顶点着色器为什么只有 `position + vec4(-1,1,0,0)`？投影矩阵去哪了？**

答：旋转/缩放/平移在 CPU 用定点矩阵算完，`screen_trans` 已把坐标映射到 x∈[0,2]、y∈[-2,0]，VS 只需平移 (-1,+1) 得到 NDC。所以精灵程序不需要投影矩阵 uniform；离屏 blit 程序才用 uniform `st` 在 GPU 做变换。

**Q6. `rs_commit` 里画 N 个矩形，为什么索引数是 `6*N`？一次 commit 对应几个 draw call？**

答：每个矩形 2 个三角形、共享 4 顶点，需要 6 个索引（0 1 2 / 0 2 3），N 个就是 6N；一次 `rs_commit` 触发一次 `glDrawElements`，即恰好 1 个 draw call（`RS->drawcall++`）。

**Q7. VAO 里的 `change_vb` 用 memcmp 比较两个数组，目的是什么？**

答：比较"当前期望绑定的 VBO 槽位组合"和"这个 VAO 已记录的组合"。相同就跳过 bind 和一整串 `glVertexAttribPointer`，不同才重设并回写，从而在连续多批共用同一 VBO/布局时省掉大量 GL 状态调用。
