## 1. 本讲地图

```
普通 picture：美术预制纹理 + 预制 UV，启动时传一次 GPU，运行时只出矩形  ← 第二讲 A/B
────────────────────────────────────────────────────────────────────
本讲三种"运行时生成"：
  label     运行时把"字"光栅化成像素，局部上传进一张共享字体纹理，再当矩形画
  particle  CPU 算每个粒子的位置/颜色/大小，用同一张小图出大量矩形（加色混合）
  RT        先把一批矩形画进一张纹理（framebuffer），之后把这张纹理当图用
```

三者最终**都还是走第二讲 B 的那条合批流水线**（攒 4 顶点 → VBO → glDrawElements），区别只在"像素从哪来、几何谁来算、画到哪里去"。

## 2. 文字 label：运行时搭建的动态字体图集

### 2.1 为什么文字不能像图片那样预制

美术图片是**已知集合**：有哪些矩形、用纹理哪一块，导出时就定死了。文字不行——

- 会显示哪些字、多少种组合，运行时才知道（分数、昵称、对话）；
- 不可能为每种字符串预渲染一张图。

做法是：**运行时准备一张大的空白"字体图集"纹理，用到哪个字就当场把那个字画上去**。

### 2.2 一张 1024×1024 的单通道纹理 + 一个装箱器

`label_load`（label.c:30）启动时建两样东西：

```c
Dfont = dfont_create(1024, 1024);                 // CPU 侧：图集分配/查找管理器
Tex   = render_texture_create(..., TEXTURE_A8);  // GPU 侧：1024×1024 的 A8 纹理
render_texture_update(..., NULL, ...);           // 空纹理，先占显存
```

- **A8 纹理只有一个 8 位通道，存的是"覆盖率/透明度"（0~255 的灰度），不存颜色**。文字染什么色由顶点色决定（见 2.5），这样一张字体图集能写出任意颜色的字，极省内存。
- `struct dfont`（dfont.c:31）负责在这张 1024² 画布上给每个字**找空位、记录矩形、按哈希查找、按 LRU 淘汰**。

```
字体图集 1024×1024（A8 灰度）
┌──────────────────────────────────────┐
│ 你  好  H  e  l  o  W  r  d  ！ ...   │  ← 一行行装箱（按字高分行）
│    （每个字占一个小矩形 dfont_rect）    │
│           空白处留给以后新出现的字       │
└──────────────────────────────────────┘
```

装箱算法（dfont.c）：按字高分成若干**行**（`find_line` 165），在高度匹配的行里从左到右**找空隙**（`find_space` 186）；塞不下就开新行。

### 2.3 懒加载：第一次遇到某个字才生成它

`label_draw`（label.c:541）逐字遍历字符串，对每个字先查 `dfont_lookup`：

- **命中**：直接拿图集里的矩形，生成一个贴图矩形；
- **未命中**：`gen_char`（label.c:152）现场造字：
  1. FreeType 初始化字体（`font_create(FONT_SIZE=31)`、`font_glyph`），把该字光栅化到一块 CPU 灰度 buffer；
  2. `dfont_insert` 在图集里分到一个矩形 `(x,y,w,h)`；
  3. **只上传这一个小矩形**：`render_texture_subupdate` → `glTexSubImage2D`（render.c:744），把新字补进字体纹理，不动其它字；
  4. 图集真满了？先 `dfont_flush` 让旧字"变老"，再用 LRU 腾位置（见 2.6），重试一次。

```
字符串 "Hello"
 H e l 命中 → 直接画
 第二个 l/o 未命中 → FreeType 画字 → glTexSubImage2D 补进图集 → 再画
（同一段文字第二次出现，全部命中，不再光栅化、不再上传）
```

这就是典型的**缓存 + 懒加载**：启动几乎零成本，用哪个字造哪个字，造完永久（直到被 LRU 淘汰）复用。

### 2.4 一个字就是一个贴图矩形

和 picture 完全一样的套路（`draw_rect` / `set_point`，label.c:203/213）：4 个顶点、UV 指向图集里那个字的小方块：

```c
v->tx = 字矩形左上角像素x * (65535/1024);   // 图集像素坐标 → u16 归一化 UV
v->ty = 字矩形左上角像素y * (65535/1024);
```

屏幕上字的宽高按请求字号 `size` 对光栅字号 `FONT_SIZE(31)` 等比缩放（label.c:216）。排版（左/中/右对齐、自动换行、`auto_scale`、行高字距、富文本变色、UTF-8 解码 `unicode_len`）都在 CPU 侧 `label_draw/draw_line` 里算好，输出仍然只是一串矩形。

### 2.5 颜色与描边：片元着色器怎么用 A8 图

字体纹理只有透明度，文字颜色走顶点色。对应片元着色器（shader.lua）：

```glsl
// PROGRAM_TEXT（shader.lua:68）
float c = texture2D(texture0, v_texcoord).w; // GLES2 的 A8 存在 .w（GLES3 用 .r）
float alpha = clamp(c, 0.0, 0.5) * 2.0;     // 0~0.5 这段当透明度
gl_FragColor.xyz = (v_color.xyz + v_additive.xyz) * alpha;
gl_FragColor.w   = alpha;
gl_FragColor *= v_color.w;
```

- 采到的灰度 `c` 只用来决定"这个像素有多不透明"，颜色全部乘顶点色 `v_color`——所以同一张白色/灰度图集能写出红字、绿字、任意颜色。
- **描边（edge）** 程序（shader.lua:104）把一个通道掰成两半用：`gen_outline`（label.c:85）把字芯编进 0.5~1.0、外圈描边编进 0~0.5；shader 再用两段 `clamp` 分别还原出"填充色"和"描边色"。

### 2.6 LRU 淘汰与 label_flush

- `dfont_flush`（dfont.c:111）只做一件事：`version++`。每帧结束被调用一次（帧末 `shader_flush()` 之后还有 `label_flush()`）。
- 每次用到某字，`dfont_lookup` 把它的 `version` 刷成当前版本并挪到 LRU 链表尾（dfont.c:135）；一帧没用过的字就停留在旧版本。
- 图集分配不下时，`release_space`（dfont.c:284）专门回收"版本过期"的旧字腾地方。这是一套**按帧老化的 LRU**：常用字常驻，生僻字用完即让位。

### 2.7 合批影响

- 进入文字时 `label_draw` 第一句 `shader_texture(Tex, 0)`（label.c:542），`draw_child` 还会切到 `PROGRAM_TEXT/TEXT_EDGE`（sprite.c:516）。字体纹理、文字 shader 都和精灵不同，按第二讲 B 的"冻结元组"，**这里必然切一刀、单独成批**；
- 但同一帧内**所有文字共用同一张字体图集和同一个文字程序**，所以成百上千个字（每个 1 个 quad）仍能攒成同一批，draw call 很少。

## 3. anchor 挂点与粒子系统

### 3.1 anchor 是"不画图、只提供坐标系"的空节点

资源里没有 id、只有 `{name="anchor"}` 的部件，实例化时走 `newanchor`（lsprite.c:167）：

```c
s->type = TYPE_ANCHOR;
s->flags = SPRFLAG_INVISIBLE;   // 默认不可见，自己不出像素
s->data.anchor = { ps = NULL(粒子系统), pic = NULL(粒子用的小图), mat = 单位阵 };
```

它有两个用途：

1. **提供一个随父节点变换的坐标点/世界矩阵**（挂点）。递归绘制到 anchor 时，`anchor_update`（sprite.c:429）把当前累乘出来的世界矩阵存进 `s->s.mat`——Lua 里读到的 anchor `world_matrix` 就是它（比如炮管尖点当前朝哪、在哪，粒子就从哪发射）。
2. **挂一个粒子系统**：`ps` 非空时，这个点既更新坐标，也负责画粒子。

### 3.2 粒子在 CPU 模拟

粒子系统移植自 cocos2d-x（particle.c 开头注明）。配置 `particle_config` 描述：生命、初/末颜色及抖动、初/末大小、初/末旋转、发射方向/速度、重力模式或半径模式、发射率、混合方式等。

每帧 `particle_system_update(dt)`（particle.c:283）在 **CPU 用浮点**模拟：

```
按发射率计时，到点 _addParticle 生成新粒子（_initParticle 随机化初值，particle.c:39）
对每个存活粒子积分 _update_particle（particle.c:181）：
   重力模式：速度 += (重力+径向+切向加速度)*dt；位置 += 速度*dt
   半径模式：角度 += 角速度；半径 += 半径变化
   大小/颜色/旋转 线性插值到"末态"
生命 -dt，归零就移除（末尾粒子搬到空洞，O(1) 删除）
```

### 3.3 渲染：同一张小图 × 每粒子矩阵，攒成一大批

`draw_child` 遇到带粒子的 anchor（sprite.c:520）调 `drawparticle`（sprite.c:474）：

```c
shader_blend(ps->config->srcBlend, ps->config->dstBlend); // 火焰常用加色混合
for 每个粒子 i:
    calc_particle_system_mat(...)   // 由 旋转/大小/位置 + 发射器矩阵 造一个矩阵
    s->t.mat   = 该粒子矩阵;
    s->t.color = 该粒子当前颜色;
    sprite_drawquad(pic, NULL, &s->t);  // 用同一张小图 pic 出 1 个 quad
shader_defaultblend();                    // 恢复默认混合
```

关键洞察：

- 每个粒子只是**同一个小贴图（如一个光点）配上不同的矩阵和颜色**，位置/大小/旋转/透明度都编码进顶点；
- 因为纹理相同，成百上千个粒子 quad 能**合批成一次 draw call**；
- 火焰/光效通常用**加色混合**（`shader_blend`，进入/退出时各切一次，按冻结元组这会在粒子前后各产生一次批次封口）；
- **模拟在 CPU、渲染完全复用精灵的矩形流水线**——这是这套引擎"万物皆贴图矩形"设计的又一个体现。

`examples/ex03.lua`：`particle.new("fire")` 得到的 `ps.group` 就是含 anchor 的精灵树；`update` 里 `ps:update(0.0333)` 做模拟，`drawframe` 里 `ps.group:draw()` 渲染。

## 4. 离屏渲染：render target（framebuffer）

正常流程里，`glDrawElements` 的结果写进**默认帧缓冲**（窗口那张图），swapbuffers 上屏。离屏渲染是：**先把结果写进一张纹理，之后把这张纹理当普通图片用**（后处理、小地图、镜子、把复杂静态画面烘一次等）。

### 4.1 framebuffer = 一张被"挂"为渲染目标的纹理

`render_target_create`（render.c:826）→ `create_rt`（render.c:805）：

```c
glGenFramebuffers(1, &fb);
glBindFramebuffer(GL_FRAMEBUFFER, fb);
glFramebufferTexture2D(fb, GL_COLOR_ATTACHMENT0, GL_TEXTURE_2D, tex, 0); // 纹理挂到颜色输出
glCheckFramebufferStatus(...);   // 确认完整可用
```

引擎封装在 `lib/texture.c`：

- `texture_new_rt(id,w,h)`（texture.c:100）：建一张空纹理 + 一个 framebuffer，并把两者绑定（`render_target_create` + `render_target_texture`）；
- `texture_active_rt(id)`（texture.c:123）：`render_set(TARGET, fb)`，下一帧提交时 `glBindFramebuffer` 切过去——**此后的绘制都写进这张纹理**；
- 切回屏幕：绑定默认 framebuffer（render.c:885，id 为 0 时用启动时记录的 `default_framebuffer`）。

### 4.2 数据流

```
① 建 RT：空纹理 T + framebuffer F（T 挂在 F 的颜色输出上）
② glBindFramebuffer(F)：画一批精灵 ──▶ 像素写进 T（不上屏）
③ glBindFramebuffer(默认)：回到屏幕
④ 把 T 当普通纹理，用一个矩形采样画到屏幕（可再做缩放/特效）
```

这也解释了第二讲 B 里 `render_state_commit` 为什么有 `CHANGE_TARGET`：渲染目标和纹理/混合一样，是"当前绘制状态"的一部分，切换它同样会改变后续 draw 的去向。

## 5. 名称辨析：renderbuffer 其实是"几何缓存"，不是离屏纹理

ejoy2d 里有个很容易误导的名字：Lua 里的 `ejoy2d.renderbuffer`（`lib/renderbuffer.c` / `lrenderbuffer.c`，示例 ex07）**不是 framebuffer、不渲染到纹理**。它是一个**保留模式的几何缓存**：

- `renderbuffer.new()`：另开一个和全局 `RS->vb` 同构的 CPU 顶点数组 `struct render_buffer`（renderbuffer.h:26）；
- `rb:add(sprite)`：现在就把精灵递归成顶点攒进去（`renderbuffer_drawsprite`，renderbuffer.c:225），**不依赖每帧重算**；
- `rb:upload()`：把这些顶点传进一个**专用 VBO**（`renderbuffer_upload`，renderbuffer.c:233），一次；
- `rb:draw(x,y,scale)`（`shader_drawbuffer`，shader.c:214）：切到这个专用 VBO，用 `PROGRAM_RENDERBUFFER` 程序、靠 uniform `vec4 st` 在顶点着色器里做平移缩放（shader.lua:235），把缓存的几何重画一遍。

ex07 把 100 只鸟 `add` 一次、`upload` 一次，之后每帧只 `rb:draw(p,p)` 平移重画——**几何只算一次、传一次，之后每帧一道工单复用**，适合大量静态内容。它采样的仍是鸟自己的纹理（`rb->texid` 记录首个 quad 的纹理）。

对比记忆：

| 名字 | 本质 | 输出到哪 | 典型用途 |
| --- | --- | --- | --- |
| `renderbuffer`（ex07） | CPU 顶点数组 + 专用 VBO（几何缓存） | 仍是屏幕 | 静态场景只烘焙一次、反复重画 |
| render target / framebuffer（texture.c） | 可写入的纹理 | 一张纹理 | 后处理、小地图、动态贴图 |

## 6. 三者与主流水线的关系

```
                    ┌─ label：FreeType 光栅化字 → glTexSubImage2D 补进字体图集(A8)
精灵树递归 draw_child ┼─ anchor：更新世界矩阵；若挂粒子 → CPU 模拟 → 同图大量 quad(加色混合)
                    ├─ picture：普通贴图矩形（第二讲 A）
                    └─ （目标可切换）画到屏幕默认 framebuffer 或 render target 纹理
                              │
                              ▼  全部汇入第二讲 B 的合批
              renderbuffer_add 攒顶点 → rs_commit → VBO → glDrawElements
静态几何还能预先烘焙进 renderbuffer 的专用 VBO，用 st uniform 重画
帧末：shader_flush（精灵批次）→ label_flush（字体图集老化）→ swapbuffers
```

一句话：**label 解决"像素运行时从哪来"，粒子解决"大量相似小图怎么 CPU 模拟、GPU 一批画完"，render target 解决"画完的东西去哪"，而它们脚下踩的都是同一条矩形合批流水线。**

## 7. 术语表

| 术语 | 一句话 |
| --- | --- |
| 字体图集 glyph atlas | 一张大纹理，把用到的字逐个画进去，字只占其中一个小矩形 |
| A8 纹理 | 单通道（仅透明度/覆盖率）纹理，颜色靠顶点色，省内存且可任意染色 |
| FreeType | 把矢量字体光栅化成位图的库（font_create/font_glyph） |
| 懒加载光栅化 | 第一次用到某字才渲染并上传，之后命中缓存 |
| glTexSubImage2D | 只更新纹理的一个子矩形（用来把新字补进图集） |
| 图集装箱 / LRU | 给字分空位；按帧老化、空间不足时淘汰最久没用的字 |
| anchor 挂点 | 不可见空节点，提供随父级变换的世界矩阵，可挂粒子 |
| 粒子系统 | CPU 侧按物理/插值模拟大量小点，渲染为同图多 quad |
| 加色混合 additive | 光效常用，颜色相加变亮；粒子按配置切换 blend |
| framebuffer / RT | 渲染目标；一张被挂为颜色输出、可被绘制写入的纹理 |
| glFramebufferTexture2D | 把纹理挂到 framebuffer 的颜色附件上 |
| renderbuffer（本引擎） | 易混名：实为"几何缓存/专用 VBO"，不是渲染目标 |
| st uniform | RENDERBUFFER 程序里对缓存几何做平移缩放的 vec4 参数 |

## 8. 自测题与答案

**Q1. 为什么文字要用运行时字体图集，而不是像美术图那样预制纹理？**

答：显示什么字运行时才知道，组合无穷，无法预制。于是准备一张共享字体纹理，用到哪个字就用 FreeType 当场光栅化、`glTexSubImage2D` 补进图集，之后复用。

**Q2. 字体纹理为什么用 A8 单通道？红字、绿字是怎么来的？**

答：A8 只存每个像素的覆盖率（透明度），不存颜色，最省。文字颜色由顶点色提供，片元着色器用采到的灰度作 alpha、再乘顶点色，所以同一张图集能染任意颜色。

**Q3. 第一次显示一个没见过的字，CPU/GPU 各发生了什么？**

答：CPU：FreeType 把字光栅化成灰度位图、dfont 在图集里分配矩形；GPU：`glTexSubImage2D` 只把这个字的小矩形上传进字体纹理；然后该字作为一个贴图 quad 进入合批。第二次再出现就直接命中、不再光栅化上传。

**Q4. anchor 节点自己会出像素吗？它存在的意义是什么？**

答：默认不可见、不出像素。它提供一个随父节点变换的坐标系/世界矩阵（可被读取，用来定位），并可挂载粒子系统；挂了粒子时由它负责画粒子。

**Q5. 成百上千个粒子为什么通常只要很少的 draw call？**

答：所有粒子用同一张小纹理，差别只在每粒子的矩阵（位置/大小/旋转）和颜色，这些编码进各自的顶点，纹理不变就能合批；加色混合只在粒子批次前后各切一次。

**Q6. 粒子的运动是 GPU 算的吗？**

答：不是。位置/速度/颜色/大小/生命在 CPU 用浮点积分（particle.c），GPU 只负责把算好的大量矩形画出来。

**Q7. 什么是 render target？把场景画进 RT 后怎么用它？**

答：RT 是一张通过 framebuffer 挂为颜色输出的纹理。绑定它之后绘制就写进这张纹理而不上屏；切回默认 framebuffer 后，可把这张纹理当普通图采样绘制（后处理、小地图等）。

**Q8. ex07 的 `renderbuffer` 是渲染到纹理吗？它解决什么问题？**

答：不是。它是"几何缓存"：把精灵的顶点预先烘焙进一个专用 VBO（add/upload 一次），之后每帧用 RENDERBUFFER 程序和 `st` uniform 重画。适合大量静态内容，省掉每帧重新递归和传顶点。
