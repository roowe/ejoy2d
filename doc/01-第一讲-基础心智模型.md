## 1. 屏幕本质上是一块"像素格子"

把窗口放大无数倍，它就是一个方格网。比如 1024×768 的窗口，一共约 78 万个小格子。每个格子只能存**一个颜色**，颜色用四个数表示：

```
R(红) G(绿) B(蓝) A(透明度)，每个分量 0~255
```

显存里有一块内存，专门存放"每个格子是什么颜色"，叫 **帧缓冲 framebuffer**（可以理解成一块画布）。你在窗口里看到的任何画面，本质都是这块内存被搬到屏幕上。

所以"画图"的本质极其朴素：

> **往这块格子内存里填颜色。**

游戏 60 帧/秒，就是每秒把这块画布重新填 60 次。

ex01 里的 `ej.clear(0xff808080)`，干的就是"先把整块画布刷成灰色"。

## 2. CPU 与 GPU 分工，OpenGL 是什么

- **CPU**：像几个武功高强的老师傅，核心少、擅长复杂逻辑（判断、循环——"炮塔该转到第几帧"就是它算的），但同时干的活不多。
- **GPU**：像几千个没什么文化但人数惊人的小工，每个人只会做一道简单工序，但可以**同时**对成千上万个格子做同一道工序。

填 78 万个格子这种"重复、量大、简单"的活，正是 GPU 的主场。

**OpenGL** 是什么？就是 CPU 给 GPU 下命令用的一套"标准菜单 / 方言"。你说一句 `glDrawElements`（画！），显卡驱动把它翻译成 GPU 能懂的电信号。`lib/opengl.h` 只是因为 Mac、Linux、安卓方言略有不同，做了"到哪说哪的话"的切换。

最重要的心理模型是这个分工：

```
CPU（C / Lua 代码）             GPU（几千个小工）
  准备好数据  ── 上传 ──►         数据放在显存里
  下命令"画"  ──────────►         并行计算，填格子
                               └─► 写进帧缓冲画布
```

注意"上传"和"下命令"这两个箭头：**CPU 和 GPU 是两块芯片，它们之间沟通是有成本的**。这个细节先记住，第 11 节整套合批机制都是为了省这个成本。

## 3. GPU 只会画三角形，万物皆三角形

GPU 并不认识"图片""精灵""炮塔"。它最底层只会画三样东西：**点、线、三角形**。

- **顶点 vertex**：一个"锚点"，就是一个坐标点。
- 3 个顶点围成一个**三角形 triangle**。
- 任何复杂形状都用小三角形拼出来（圆形也一样，只是三角形很多）。

2D 里最常画的是矩形，矩形 = **2 个三角形**，用 4 个角：

```
   0 ───────── 1
   │  ╲        │        三角形一：0 → 1 → 2
   │    ╲      │        三角形二：0 → 2 → 3
   3 ───────── 2
```

4 个顶点，但要列出 6 个"连接顺序"：`0 1 2  0 2 3`。这 6 个数字就是**索引（index）**。

代码里到处出现的 `quad`（四边形），就是"一个矩形 = 两个三角形"的打包单位。

> 为什么硬件偏爱三角形？因为三个点一定共面、形状唯一确定，不会凹来凹去，电路最好实现。

## 4. 重点答疑：为什么 4 个顶点却要 6 个索引（索引绘制）

这一节回答自测第 1 题，背后是一个核心设计：**索引绘制（indexed drawing）**。

### 4.1 如果没有索引会怎样

一个矩形 = 2 个三角形。假设你只有一个顶点列表，规定"每 3 个点画一个三角形"，那你得这样列：

```
三角形 A：左上角、右上角、右下角
三角形 B：左上角、右下角、左下角
```

数一下：**要写 6 个顶点**。但矩形明明只有 4 个角——左上角写了 2 次，右下角也写了 2 次。

```
不用索引：要存 6 份顶点数据（重复的角连同它的 UV、颜色都要再写一遍）

  0左上  1右上  2右下 │ 0左上  2右下  3左下
  └─────三角形 A─────┘ └─────三角形 B─────┘
            左上(0) 和 右下(2) 各重复了一次
```

顶点不只是一个坐标，它还带着 UV、颜色、加亮色（第 6 节的 `struct vertex`）。重复角 = 把这些数据也重复存一遍，浪费显存和带宽；而且两份"同一个角"的数据万一不一致，两个三角形的接缝处会出现裂缝。

### 4.2 解决办法：把"有哪些点"和"怎么连"拆成两张表

**第一张表：顶点缓冲 VBO —— "花名册"，每个唯一的角只存一次**

```
编号      位置      UV     颜色
[0]    左上角      ...    ...
[1]    右上角      ...    ...
[2]    右下角      ...    ...
[3]    左下角      ...    ...
```

**第二张表：索引缓冲 IBO —— "分镜脚本"，里面只放编号**

```
三角形 A：  0 → 1 → 2
三角形 B：  0 → 2 → 3
合起来就是 6 个数字：0 1 2 0 2 3
```

于是：**顶点只有 4 个（4 个角），索引有 6 个（两次"3 个点一组"的连线指令）**。索引不是新的点，它只是一句"去花名册里查第几号点"的引用。

一个类比：

- **VBO 是演员名单**（4 个演员，各有各的资料）；
- **IBO 是分镜脚本**（第 1 场让 0、1、2 号演员出场，第 2 场让 0、2、3 号出场）。同一个演员可以在多场戏里出场，但他的资料只登记一份。

### 4.3 对应到代码

引擎在启动时预生成这张索引表（`lib/shader.c:90-99`）：

```c
for (i = 0; i < MAX_COMMBINE; i++) {
    idxs[i*6+0] = i*4;        // 第 i 个矩形的 0 号角
    idxs[i*6+1] = i*4 + 1;    //                1 号角
    idxs[i*6+2] = i*4 + 2;    //                2 号角
    idxs[i*6+3] = i*4;        //                0 号角（复用）
    idxs[i*6+4] = i*4 + 2;    //                2 号角（复用）
    idxs[i*6+5] = i*4 + 3;    //                3 号角
}
```

合批 1024 个矩形时：顶点是 `1024 × 4` 个，索引是 `1024 × 6` 个，所以绘制调用是
`render_draw(DRAW_TRIANGLE, 0, 6 * object)`（`lib/shader.c:197`），里面乘的 6 就是这么来的。

### 4.4 索引绘制的两个额外好处

1. **省内存 / 省带宽**：共享的角不重复。一个矩形只是 4 vs 6，差别不大；但一个有几千个相邻三角形的复杂网格，共享顶点非常多，节省巨大。
2. **顶点着色器结果可复用**：0 号、2 号角虽然各被两个三角形引用，但顶点只存一份，GPU 会缓存它们经过顶点着色器变换后的结果，不重复计算。

> 补充：三个点的排列顺序（顺 / 逆时针）还决定三角形"正面"朝哪，3D 的背面剔除会用到；2D 基本不用管，只要知道顺序不能乱写即可。

## 5. 你要给 GPU 两段小程序：着色器 Shader

你没法手把手教每个小工怎么涂色，你要给他们两张"作业指导书"，用一种叫 **GLSL** 的、长得很像 C 的语言写。这两段程序编译链接后合称一个**着色器程序 program**。

### ① 顶点着色器（vertex shader）

对**每个顶点**跑一次（一个矩形就跑 4 次）。任务：回答"这个顶点最终落在屏幕的哪个位置"，答案写进内置变量 `gl_Position`。移动、旋转、缩放都在这一步发生。

### ② 片元着色器（fragment shader，也叫片段 / 像素着色器）

三角形内部要被填满，GPU 先算出这个三角形盖住了哪些像素格子，然后对**每一个被盖住的像素**跑一次片元着色器。任务：回答"这个格子涂什么颜色"，答案写进 `gl_FragColor`。

中间那步"把数学上的三角形，变成它盖住了哪些像素格子"，有个专门的词叫**光栅化（rasterization）**，由 GPU 固定硬件完成，不用你写代码。光栅化时还会自动做**插值（interpolate）**：三个角的颜色 / UV 不同，中间像素会按位置自动平滑过渡——渐变色、贴图拉伸都是白来的。

整条流水线长这样（**这是图形学的核心，建议反复看**）：

```
 CPU 准备并上传：
   顶点数组(位置/UV/颜色) ──► 显存里的顶点缓冲 VBO
   一张图片(*.ppm)        ──► 纹理 Texture
   两段 GLSL 程序         ──► 编译成 Program
          │
          │  CPU 下令：glDrawElements（画！）
          ▼
 ┌────────────── GPU 流水线 ──────────────┐
 │ ① 顶点着色器：每个顶点跑一次，算出屏幕位置 │
 │            ▼                            │
 │ ② 按索引把顶点连成三角形                  │
 │            ▼                            │
 │ ③ 光栅化：三角形 → 盖住哪些像素 + 插值     │
 │            ▼                            │
 │ ④ 片元着色器：每个像素跑一次，算出颜色      │
 │      （取图片颜色、乘染色、处理透明）       │
 │            ▼                            │
 │ ⑤ 写进帧缓冲那块格子画布                  │
 └─────────────────────────────────────────┘
          ▼
   swapbuffers：把画布亮到窗口上
```

### 两个着色器各跑多少次？（自测第 2 题）

次数不由你决定，是 GPU 按数据量自动铺开的：

- **顶点着色器：逐顶点**。一个矩形 4 个角 → 跑 4 次；合批 1024 个矩形 → 约 4096 次。
- **片元着色器：逐被覆盖像素**。次数取决于矩形在屏幕上占多大面积。一个盖住 200×100 区域的矩形，片元着色器就跑约 2 万次；全屏清一遍就是 1024×768 ≈ 78 万次。

这就是 GPU 为什么需要几千个小工核心：**顶点着色器通常跑几千次，片元着色器动辄几百万次**。你只写一次"对一个像素怎么算颜色"，GPU 自动对几百万个像素并行铺开。

ejoy2d 普通精灵用的两段指导书在 `ejoy2d/shader.lua:14-45`，现在应该能读懂大意：

```glsl
// 顶点着色器：把位置平移到标准坐标系（见第 8 节）
gl_Position = position + vec4(-1.0, 1.0, 0, 0);

// 片元着色器：从纹理取色 → 乘染色 → 加亮
vec4 tmp = texture2D(texture0, v_texcoord);
gl_FragColor.xyz = tmp.xyz * v_color.xyz;
gl_FragColor.w   = tmp.w;
gl_FragColor    *= v_color.w;
gl_FragColor.xyz += v_additive.xyz * tmp.w;
```

## 6. 每个顶点带的"行李"：顶点属性与 uniform

每个顶点上流水线时携带的数据，正好就是 C 代码里的结构体（`lib/renderbuffer.h:16`）：

```c
struct vertex {
    float    vx, vy;   // 位置      —— 顶点着色器用
    uint16_t tx, ty;   // UV 贴图坐标 —— 片元着色器取图用
    uint8_t  rgba[4];  // 染色      —— 可以让图变红 / 变淡 / 变透明
    uint8_t  add[4];   // 加亮      —— 发光特效用
};
```

- 这种把一个顶点的多种数据排在一起的布局，叫**顶点属性格局（vertex layout）**。`lib/shader.c:104-109` 启动时注册的就是它，告诉 GPU"每个字段在顶点里的偏移和类型"。
- UV 用 `uint16_t`（0~65535）存，GPU 自动归一化成 0~1；颜色用 `uint8_t`，也是为了省内存 / 省带宽。

**uniform（一致变量）**：着色器程序的"全局可调参数"，由 CPU 传一次、本次绘制里所有顶点 / 像素共用，比如变换矩阵。`shader_setuniform` 就是在设它。它和"每个顶点各不相同"的顶点属性正好相反——uniform 是"这批顶点都一样"的参数。

## 7. 纹理 Texture 和 UV：给三角形贴贴纸

**纹理（texture）**就是一张传到 GPU 上的图片。`examples/asset/sample.1.ppm` 是一种最朴素的图片格式（PPM 几乎就是裸像素数据），启动时被读进来上传成 GPU 纹理。

你不想让三角形是纯色，想把图片"贴"上去，就得告诉它：三角形的每个角，分别对应图片上的哪个位置。这个"图片上的坐标"就叫 **UV**：

- U = 图片横向位置，0 是最左、1 是最右；
- V = 图片纵向位置，0 是一头、1 是另一头。

```
图片（纹理）                     屏幕上的矩形
┌──────────────┐               0(uv=0,0)────────1(uv=1,0)
│              │               │  ╲            │
│   一张炮塔图  │       →       │    ╲  图片被  │
│              │               │      ╲ 贴上去 │
└──────────────┘               3(uv=0,1)────────2(uv=1,1)
```

光栅化时 UV 也跟着插值，于是矩形中间每个像素都知道自己该去图片的哪个点取色——这就是片元着色器里那句 `texture2D(texture0, uv)`。

于是可以给**精灵（sprite）**下一个准确定义：

> 一个精灵 = 一个或几个"贴了某张纹理某块区域的矩形"。炮塔、地雷，本质都是贴了图的矩形。

美术导出的 `sample.lua` 记录了每个部件矩形的四角屏幕坐标（`screen_coord`）和对应的图片坐标（`texture_coord`）。

**没有 UV 能不能贴纹理？** 不能（在正常流程下）。GPU 不知道三角形的每个点该对应图片哪里，就无从采样。（理论上你能在着色器里用位置硬编码出一套坐标，但那就不叫正常的纹理映射了。）

## 8. 坐标系：GPU 用 -1 到 1，而不是像素（NDC）

顶点着色器输出的位置，不认"1024×768 像素"，它用一个标准坐标系，叫 **NDC（Normalized Device Coordinates，标准化设备坐标）**：

```
        x = -1 ─────── 0 ─────── +1
 y=+1   左上 ─────────────────── 右上
   │       │                      │
 y=0       │       屏幕中心(0,0)   │
   │       │                      │
 y=-1   左下 ─────────────────── 右下
```

而游戏用"左上角是 (0,0)、宽 1024、高 768"的设计坐标。所以要做一次换算——你懂坐标变换，这其实就是一次**缩放 + 平移**，没用投影矩阵：

- `screen_trans`（`lib/screen.c:36`）：`x × 2/宽`，`y × -2/高`；
- 顶点着色器再 `+(-1, +1)`（`ejoy2d/shader.lua:40`）。

代几个数字：

| 设计坐标 | 含义 | 换算后 NDC |
|---|---|---|
| (0, 0) | 左上角 | (-1, +1) |
| (512, 384) | 屏幕中心 | **(0, 0)** |
| (1024, 768) | 右下角 | (+1, -1) |

所以 ex01 里 `screencoord = { x = 512, y = 384, scale = 1.2 }` 的含义就是"**以屏幕中心为原点、放大 1.2 倍**画这棵精灵树"。

## 9. 透明与混合 blend

颜色第四个分量 **A（alpha）= 不透明度**。图片里炮塔之外的空白区域 alpha=0（全透明），炮塔边缘可能半透明（用于抗锯齿）。

半透明像素叠到已经画好的背景上时，新颜色和旧颜色按什么比例掺？这叫**混合（blending）**，形如：

```
最终颜色 = 新像素 × 系数1  +  旧画面 × 系数2
```

代码默认的 `BLEND_ONE / BLEND_ONE_MINUS_SRC_ALPHA`（`lib/shader.c:88`）是"预乘 alpha"的标准配法，目的是让贴图的透明边缘正确叠在背景上。**现阶段只要记住：blend 是控制透明叠加的开关，换 blend 方式属于"改变绘制状态"。**

另外三个 3D 常见状态，2D 里基本只闻其名：

- **深度测试 depth test**：决定谁挡谁，2D 按绘制顺序叠加，通常关闭；
- **背面剔除 cull**：不画背对镜头的三角形，2D 用不到；
- **裁剪 scissor**：只允许在一个矩形框内作画，用于面板裁剪。

## 10. GPU 资源与"取衣牌"：VBO / IBO / RID

GPU 资源（顶点数组、图片、shader 程序）都放在显存 / 驱动那边，你在 C 代码里拿不到直接指针，只拿到一个**编号**，像洗衣店的取衣牌：

- **VBO**（Vertex Buffer Object，顶点缓冲对象）：显存里的一个数组，你把 `struct vertex` 顶点上传进去；
- **IBO**（Index Buffer Object，索引缓冲对象）：那张 `0 1 2 / 0 2 3` 连接表；
- 纹理、program 同理，各有各的编号。

这套代码没有直接用 OpenGL 的编号，而是又包了一层叫 **RID**（`lib/render/render.h` 里 `typedef unsigned int RID`），规则是"对象池槽位号 + 1"，**0 专门表示空**。

为什么要自己管编号、自己开内存池（`carray.c` / `block.h`）？因为这是从手游 / 主机时代来的引擎，要求：

- 内存用量在游戏一开始就定死；
- 运行过程中绝不临时 `malloc`，避免卡顿；
- 绝不产生内存碎片。

配套的两个小工具：

- `block.h`：bump / 线性分配器，在外部给的一大块内存上依次切出各对象池，只往后挪指针；
- `carray.c`：定长对象池 + 自由链表，`array_alloc` 摘一个空槽、`array_free` 放回去，都是 O(1)，RID 与槽位指针用 `array_id / array_ref` 互相换算。

## 11. 最关键的优化：Draw Call 与合批

你下一次 `glDrawElements` 命令，叫一个 **draw call（绘制调用）**，意思是"用当前绑定的 VBO、IBO、shader、纹理，画这批三角形"。

draw call 是有成本的：CPU↔GPU 通信、GPU 流水线切换状态都要时间。如果画一个小矩形就下一次命令，一屏几千个矩形就是几千次命令，帧率立刻垮掉。

于是引擎的做法是——**攒着**：

```
画矩形 1：先不发命令，把它的 4 个顶点塞进 CPU 内存的大数组 RS->vb.vb
画矩形 2：继续塞
画矩形 3：继续塞 ...（最多攒 1024 个，MAX_COMMBINE）
   ...
一旦"绘制状态"要变，立刻"发车"（rs_commit / flush），
然后开始攒下一批。

"发车"时才：把整个大数组一次性上传 VBO，发一次 glDrawElements，
GPU 一口气把成百上千个矩形全画出来 —— 这就叫【合批 batching】。
```

**类比寄快递**：不是来一个包裹发一趟车，而是把同一目的地（同一纹理 / shader）的件攒满一车再发；中途要换目的地，就先把当前这车发走。

### 必须提前 flush 的时机（自测第 4 题下半）

一个 draw call 只能在**一套固定不变的 GPU 状态**下画。顶点数据本身可以一直往里加（那正是攒批），但下面这些状态一旦要变，当前这批必须先发车：

1. **要换纹理**了（`shader_texture`，不同部件用了不同图片）；
2. **要换 shader 程序**了（`shader_program`，比如从普通精灵切到文字 shader）；
3. **要换混合方式**了（`shader_blend`，比如粒子用加法发光混合）；
4. **要改 uniform 参数**了（`shader_setuniform`）；
5. 顶点数组**攒满 1024 个**矩形（`MAX_COMMBINE`）；
6. 要切去画**离屏纹理**（`shader_drawbuffer` 开头）；
7. **这一帧画完了**（`shader_flush`，把没凑满的零头也发走）。

回头看代码会发现一个统一动作：这些函数开头几乎都先喊一嗓子 `rs_commit()`——"先把上一车发走，再换新状态"，这是合批正确性的铁律。

这也解释了一个看似奇怪的现象：

- `shader_draw()` 名字叫 draw，其实**根本没画**，只是 `renderbuffer_add()` 往大数组里塞顶点（`lib/shader.c:284`）；
- 真正发命令的是 `rs_commit()`（`lib/shader.c:200`）→ `render_draw` → `glDrawElements`；
- 帧末 `shader_flush()` 保证最后剩下没凑满的一批也被发走。

ex01 里炮塔和地雷如果用同一张 `sample` 图、同一个 shader，它们那么多矩形往往**合并成 1~2 次 draw call** 就画完了。`drawcall_count()` 用来数这一帧发了几趟车。

## 12. 把一整帧串起来（ex01 发生了什么）

```
【启动，只做一次】
 1. GLFW 开出 1024×768 的窗口，背后准备好帧缓冲画布
 2. Lua 的 shader.init() 编译 9 套 shader 程序（普通精灵 / 文字 / 离屏 ...）
 3. 读 sample.1.ppm 上传成纹理；读 sample.lua 建好精灵部件数据
 4. 建 VBO（动态顶点缓冲）和 IBO（每矩形 6 索引的固定表），注册顶点布局

【每秒约 60 次，每一帧】
 5. update：turret.frame += 3，mine.frame += 1   （只是改了个整数）
 6. clear：把画布刷成灰
 7. obj:draw 遍历精灵树，把每个可见部件算成 4 个角的
    屏幕坐标（矩阵变换）+ UV + 颜色，塞进合批大数组
 8. flush：上传大数组 → glDrawElements
    GPU：顶点着色器定位 → 拼三角形 → 光栅化
         → 片元着色器采样纹理 / 染色 / 透明混合 → 写帧缓冲
 9. label_flush：文字用 FreeType 动态生成的字体纹理，另画一遍
10. swapbuffers：把帧缓冲亮到屏幕上
```

三层结构与调用方向：

```
┌─ 平台层   mac/.../window.c（GLFW 窗口 / 主循环 / 鼠标）  posix/winfw.c（胶水）
├─ 引擎层   lib/*.c（ejoy2dgame Lua 宿主、shader、sprite、renderbuffer、screen、texture）
│          lib/render/*（GL 渲染设备：句柄 + 内存池 + 脏标记延迟提交）
└─ 脚本层   lua/*（Lua 5.3 虚拟机）+ ejoy2d/*.lua（引擎 Lua 封装）+ examples/ex01.lua（游戏）
```

## 13. 动画为什么会动

第 5 步里 `frame` 只是一个不断 +1 的整数，为什么画面就动了？

因为第 7 步遍历精灵树时，会**按当前 `frame` 取"这一帧由哪些部件、用哪些 UV 区域组成"**（见 `lib/renderbuffer.c` 里 `TYPE_ANIMATION` 分支对 `ani->frame` 的索引）。

你并没有真的移动图片，而是每帧贴了**不同的纹理区域 / 摆放了不同的子部件**，视觉上就动起来了——和翻页动画（手翻书）是同一个原理。炮塔转得快（每帧 +3）、地雷播得慢（每帧 +1），只是这个整数增长得快慢不同。

## 15. 自测题与答案

**Q1. 为什么一个矩形需要 4 个顶点却要 6 个索引？**

答：矩形由 2 个三角形组成，每个三角形需要 3 个顶点的连线指令，所以要 3×2=6 个索引；但 4 个角是两个三角形共享的，用索引引用后顶点只需存 4 份（`0 1 2` 和 `0 2 3`，其中 0、2 各复用一次）。这样省内存 / 带宽、避免接缝、顶点变换结果还能被缓存复用。详见第 4 节。

**Q2. 顶点着色器和片元着色器分别对"谁"、各跑多少次？**

答：顶点着色器**逐顶点**跑，一个矩形跑 4 次，负责算每个角的屏幕位置；片元着色器**逐被三角形覆盖的像素（片元）**跑，跑多少次取决于矩形在屏幕上占多少像素，负责算每个像素的颜色。中间由硬件做光栅化和插值。

**Q3. UV 是干什么用的？没有它能不能贴纹理？**

答：UV 指定三角形每个角对应纹理图片上的哪个位置，光栅化时插值，片元着色器据此 `texture2D` 取色。没有 UV，GPU 不知道像素该取图片哪里，正常流程下无法贴纹理。

**Q4. 为什么引擎要把矩形攒到 1024 个才画一次？什么情况下必须提前 flush？**

答：为了把成百上千个小矩形合并成一次 draw call，减少 CPU↔GPU 通信和状态切换开销。当**绘制状态**要改变时必须提前 flush：换纹理、换 shader、换混合、改 uniform、攒满 1024、切离屏、以及每帧结束。

**Q5. 屏幕中心 (512, 384) 最终被顶点着色器输出成 NDC 的几？**

答：(0, 0)。左上角 (0,0) → (-1,+1)，右下角 (1024,768) → (+1,-1)。
