## 1. 先分清：资源是"模具"，精灵是"产品"

这是本讲最重要的心智模型。很多人读不懂这套代码，是因为把两份数据搞混了。

```
sample.lua（美术导出的 Lua 表 / 文本）
      │  pack.pack(...) 编译，只做一次
      ▼
sprite_pack（模具 / 预制件，只读、全局共享）
      · 每个图片块的纹理坐标、本地顶点坐标
      · 每个动画有哪些部件、每一帧怎么摆
      · 纹理本身（sample.1.ppm 上传到 GPU）
      │
      │  ej.sprite("sample","cannon")  →  c.new 递归实例化
      ▼
struct sprite 树（实例 / 产品，可变、每个对象一棵）
      · 当前在第几帧 frame
      · 自己的位置 / 缩放 / 旋转 / 颜色
      · 指向父节点、子节点
```

- **模具（pack）**：一份就够，所有 cannon 共享，里面是"大炮长什么样、怎么动"的静态描述。
- **实例（sprite）**：你每调一次 `ej.sprite(...)` 就造一棵新树。两个 cannon 实例可以一个朝左、一个朝右、各自播各自的帧，但它们**共用同一份模具数据和同一张纹理**，省内存。

类比：**图纸 vs 按图纸造出来的汽车**；**类 vs 对象**；**皮影的人偶部件谱 vs 台上这一个被操纵的人偶**。

## 2. 资源包 sample.lua 里有哪些节点

`sample.lua` 本质是一个大数组，每项是一个节点，靠 `id` 编号、靠 `type` 区分类型：

| type | 含义 | 是不是叶子 | 对应常量 |
|---|---|---|---|
| `picture` | 一块（或多块）贴图矩形，真正会出像素 | 叶子 | `TYPE_PICTURE` |
| `animation` | 容器：若干部件 + 一串帧 | 容器（有孩子） | `TYPE_ANIMATION` |
| `polygon` | 多边形贴图 | 叶子 | `TYPE_POLYGON` |
| `label` | 文字（运行时用 FreeType 生成纹理） | 叶子 | `TYPE_LABEL` |
| `pannel` | 面板容器，可开矩形裁剪 | 容器 | `TYPE_PANNEL` |
| `anchor` | 挂点 / 空节点，**自己不画图**，只提供一个坐标系（常用来挂粒子） | 特殊 | `TYPE_ANCHOR` |
| `matrix` | 一段纯矩阵数据 | — | `TYPE_MATRIX` |

两个"名字"概念要分清：

- `export = "cannon"`：写在某个 animation 上，表示**这个根节点可以被 `ej.sprite("sample","cannon")` 按名字取到**。
- component 里的 `name = 'turret'`：表示**这个子部件可以在 Lua 里用 `obj.turret` 按名字访问**。

## 3. picture 叶子：src 与 screen 两套坐标

一个 picture 节点长这样（sample.lua:7）：

```lua
{ type="picture", id=0,
  { tex=1,
    src    = { 226,61, 226,94, 254,94, 254,61 },   -- 纹理上的 4 个点（像素坐标）
    screen = { -382,-640, -382,428, 514,428, 514,-640 } } } -- 矩形 4 角的本地坐标
```

它描述"把纹理图上的某一块，贴到本地坐标系里的一个矩形上"：

```
纹理 sample.1.ppm（像素格子）          精灵的本地坐标系（原点在精灵中心）
┌──────────────────────┐
│  src：在图上抠哪一块    │            screen：4 个角摆在哪里
│  （4 点，纹素像素）     │     →      （4 点，内部坐标 = 1/16 逻辑像素）
└──────────────────────┘
```

- `src`（source，源）：8 个数 = 4 个点的 `(x,y)`，是**纹理图片上的像素位置**。编译时会换算成第一讲说的 UV（0~1）。
- `screen`（目标）：8 个数 = 矩形 4 个角在**精灵本地坐标系**里的位置。注意它用的是引擎**内部坐标单位：1 个内部单位 = 1/16 个逻辑像素**（`SCREEN_SCALE = 16`，spritepack.h:17），原点大致在精灵中心，所以有正有负。例如 id0 的 x 从 -382 到 514，换算成逻辑像素约是 -24 到 32。
- 两组 4 个点一一对应，于是 GPU 知道"图片这一角"贴到"矩形那一角"。这正是第一讲 UV 映射的数据来源。
- `tex=1` 表示用第 1 张纹理（一个包可以含多张图）。

一个 picture 可以含多个这样的四边形（`struct pack_picture { int n; struct pack_quad rect[1]; }`，`rect[1]` 是柔性数组写法，实际有 n 个）。

## 4. animation 容器：component 花名册 + frame 帧表

animation 是这一讲的核心，它由两部分组成：

```lua
{ type="animation", id=19,
  component = {            -- ① 部件花名册：这个动画由哪些子节点组成
    {id=1},{id=0},...,{id=18},
    { name="anchor" },     --    没有 id 的是挂点(anchor)
  },
  {                        -- ② 帧表：数组，每一项 = 一帧
    { {index=19, mat={724,-724,724,724,565,565}} },   -- 这一帧：19号部件用这个矩阵
    { {index=19, mat={741,-706,706,741,551,578}} },   -- 下一帧：矩阵变了 → 动起来
    ...
  }
}
```

数据结构对应关系（`lib/spritepack.h`）：

```
animation
├─ component[]   花名册：每项 { 子节点id, 可选名字 }
│                 └─ 运行时每个 component 槽位挂一棵子精灵树
└─ frame[]       帧表：frame[k] 是第 k 帧
                  └─ 这一帧是一个 parts 列表，每个 part：
                       { index = 用花名册里哪个部件,
                         mat   = 这一帧该部件相对父节点的【局部矩阵】,
                         touch = 能否点中(可选) }
```

关键点：

1. **部件（component）是静态花名册**，说"我由谁组成"；
2. **帧（frame）是动态清单**，说"这一帧显示谁、各自摆在什么姿势（局部矩阵）"。某一帧可以只列部分部件，也可以让同一部件用不同矩阵；
3. 帧表里**相邻帧的矩阵略有不同**，快速翻帧就形成旋转/摆动——这就是动画的全部秘密（第一讲结尾提过，这里看到了数据本体）。

## 5. 两棵真实的树：cannon 与 mine

### cannon（id=26，`export="cannon"`，只有 1 帧）

```
cannon (animation, 帧: {0,1,2})
├─ component[0] → id24 picture   底座之类
├─ component[1] → id25 picture   轮子之类
└─ component[2] → id19 animation，名字 "turret"   ← Lua 里 obj.turret
                   ├─ component: id1..id18 一堆 picture（炮管不同朝向/部件）
                   ├─ component: "anchor" 挂点（粒子挂这）
                   └─ 几十上百帧：每帧调整部件矩阵（炮管扫过一圈）
```

根 cannon 只有 1 帧，所以它本身"不动"；真正在动的是子动画 **turret**。这解释了 ex01 为什么 `turret.frame = turret.frame + 3` 能让炮管转、而底座不动。

### mine（id=38，`export="mine"`，1 帧）

```
mine (animation)
├─ id34 / id35 / id36 / id37 picture   地雷的各张图片部件
├─ id33 animation                      一个小动画（闪光/旋转之类）
├─ id23 animation，名字 "resource"      资源条，带 touch=true（可点）
├─ id39 label，名字 "label"            ← Lua 里 obj2.label，可设 .text
└─ id40 pannel，名字 "panel"           面板（可裁剪）
```

ex01 里 `obj2.label.text = ...`、`obj2.resource.frame = 70`，就是按 component 名字 / 直接访问子节点。

## 6. 变换用"定点矩阵"表示

你熟悉 2D 仿射变换，这里只讲这套引擎的**工程写法：定点数 + 6 个数**。

### 6.1 六个数就是一个 2D 仿射矩阵

`lib/matrix.h`：

```
| m[0] m[1] 0 |
| m[2] m[3] 0 |
| m[4] m[5] 1 |        点用行向量 | x y 1 |，变换方式：p * m
```

- `m[0..3]`：旋转 + 缩放（2×2 线性部分，无量纲）；
- `m[4], m[5]`：平移（tx, ty，**内部坐标单位 = 1/16 逻辑像素**）。

### 6.2 两套定点刻度，别混在一起

这套引擎有**两套互相独立的定点约定**，读代码时一定要分开：

1. **线性量（旋转/缩放系数 m[0..3]）：1024 表示 1.0**，用到时 `/1024`；
2. **坐标量（顶点 screen_coord、平移 m[4]/m[5]）：16 个内部单位表示 1 个逻辑像素**（`SCREEN_SCALE = 16`）。

老移动端为了省浮点、要确定性才这么做。对照例子：

- 单位矩阵：`{1024, 0, 0, 1024, 0, 0}`（代码 `matrix_identity`）；
- `{1024,0,0,1024,0,800}`：线性部分为单位，y 平移 **800 个内部单位 = 800/16 = 50 个逻辑像素**。平移量不参与 `/1024`（它不是系数），但最终上屏前会被 `screen_trans` 里的 `/16` 换算（见 §11）；
- 水平镜像：`{-1024,0,0,1024,0,0}`（m[0]=-1，炮管朝左/朝右切换就是它）；
- 旋转约 45° 并平移：`{724,-724,724,724,565,565}`，因为 724/1024 ≈ 0.707 = cos45° = sin45°；其中平移 (565,565) 内部单位 ≈ (35,35) 逻辑像素。

> 单位换算的代码证据：Lua 传进来的逻辑像素在进入引擎时 `×16`（`lsprite.c:131 srt->offx = x*SCREEN_SCALE`、`lmatrix.c:71`），读回 Lua 时 `/16`（`lsprite.c:394`、`sprite.c:625`），上屏归一化也 `/16`（`screen.c:28 invw = 2/SCREEN_SCALE/w`）。而资源编译器 `spritepack.c` 里**没有** SCREEN_SCALE 换算，所以 sample.lua 里写死的 `screen`、`mat` 数值本来就是内部单位。

你在 sample.lua 帧表里看到的一大堆 6 元组，全是这种定点矩阵。

### 6.3 角度也是定点：1024 个单位 = 90°

`lib/matrix.c` 用一张 2048 项的余弦查找表 `icost` 避免实时三角函数：

- 0 单位 = 0°（cos=1024）；
- 1024 单位 = 90°（cos=0）；
- 整圈 360° = 4096 单位；
- `sin(d) = cos(1024 - d)`。

### 6.4 SRT 与矩阵复合

- SRT = Scale（缩放）、Rotate（旋转）、Translate（平移）。`struct srt { offx, offy, scalex, scaley, rot }` 是给 Lua 用的"人话版"变换。
- `matrix_srt` 按 **先缩放 → 再旋转 → 再平移** 的顺序合成（matrix.c:250）。
- `matrix_mul(out, A, B)` 算 `out = A * B`，线性部分相乘后 `/1024`，平移项按仿射公式合并（matrix.h:26）。

> ⚠️ **顺序警告：本引擎用行向量，和多数 OpenGL 教材的列向量约定相反，千万别直接套。**
>
> - 本引擎点是**行向量**，写法 `p * m`（matrix.h:6-21 明确写了 `p * m`）。于是"**先做 A、再做 B**"合成出来就是 `A * B`：因为 `p` 先过 A 得 `p*A`，再过 B 得 `(p*A)*B = p*(A*B)`。
> - 而列向量教材（GLSL 习惯 `m * p`）里，"先 A 后 B"要写成 `B * A`。
> - 两者几何结果完全一样，只是乘法左右镜像。本讲一律按**行向量**讲：`A * B` = 先 A 后 B。

## 7. 核心：父子嵌套，世界矩阵一层层乘出来

这是本讲的灵魂。树里每个部件只存"**相对父节点**的局部矩阵"（帧表里的 `mat`）。递归**遍历**是从根走到叶子，但矩阵**累积**方向要按行向量规则来：每深入一层，就把"本部件的局部矩阵"乘在"父级已累积矩阵"的**左边**，于是局部矩阵离点最近、最先作用：

```
叶子角点 p 的最终位置 = p · M_world，其中

M_world = M_part × M_parent × … × M_root × M_srt
          └─ 离点最近、最先作用 ─┘   └─ 最后作用（摆到屏幕）┘

展开成对点的连乘（行向量，从左到右即作用先后）：
  p × M_part × M_parent × … × M_root × M_srt
  （M_part=该部件这一帧的局部矩阵；M_srt=draw 时传的 x=512,y=384,scale=1.2）
```

代码正是这个顺序：`sprite_trans_mul2(pack, &pp->t, t父, ...)`（sprite.c:344）先让结果等于部件局部矩阵 `pp->t`，再在 `sprite_trans_mul_` 里算 `t = M_part × t父`（sprite.c:328 即 `matrix_mul(out, M_part, M父)`）；到叶子 `matrix_srt` 再把 SRT 右乘到最后（sprite.c:28）。

> 对照列向量教材：那里会写成 `M_srt × … × M_parent × M_part × p`（根在最左）。几何结果相同，只是整体左右镜像。本引擎记住一句：**行向量、局部矩阵在最左、从局部向父级累积**。

直观理解——**提线木偶 / 皮影**：

```
身体平移了，挂在身体上的手、手里的枪都跟着走；
手自己又能相对身体旋转；枪相对手再转一点。
最终枪尖位置 = 每一级变换的累乘。
```

- cannon 整体 `obj:ps(-100,0,0.5)`：给的是**根**的变换（左移 100、缩小 0.5），炮管和底座一起被搬动；
- 炮管 turret 帧表里的旋转矩阵：是**相对底座**的局部变换，只转炮管。

递归绘制的代码在两处（逻辑相同）：

- 正常路径 `lib/sprite.c: draw_child()`（497 行起）：遍历当前帧每个 part，算出 `ct = M_part × 父累积变换`（局部在左），再递归孩子；遇到 picture 叶子就交给第一讲的 `shader_draw` 攒四边形；
- 离屏路径 `lib/renderbuffer.c: drawsprite()` 的 `TYPE_ANIMATION` 分支（175 行起）逻辑一样。

## 8. frame 三件套与循环动画

每个动画实例（`struct sprite`）有三个帧字段：

| 字段 | 含义 |
|---|---|
| `start_frame` | 从帧表的第几帧开始（用于动作片段 action） |
| `total_frame` | 这段动作一共多少帧（0 表示不动画） |
| `frame` | 当前播放到第几帧（可变状态） |

取帧逻辑（`get_frame`，sprite.c:220）：

```c
f = frame % total_frame;      // 取模 → 自动循环；负帧会加回一圈
if (f < 0) f += total_frame;
return f + start_frame;       // 落到帧表真实下标
```

于是 ex01 的逻辑帧：

```lua
turret.frame = turret.frame + 3   -- 每次推进 3 帧（转得快）
obj2.frame   = obj2.frame + 1     -- 推进 1 帧（播得慢）
```

- `% total_frame` 保证播完自动跳回开头，无限循环；
- **每个动画实例各有各的 `frame`**：根 cannon 只有 1 帧（`total_frame=1`，永远停在那一帧），子动画 turret 有几十帧独立播放——所以"底座不动、炮管自己转"。

> 动作片段 action（`pack_action`）：可以给帧表的某段区间起名字（如 "idle"/"fire"），`sprite_action` 设置 start_frame/total_frame 来切动作。sample.lua 没用到，知道即可。

## 9. 运行时精灵树如何从模具实例化

`ej.sprite("sample","cannon")` 在 C 侧的过程（`lib/lsprite.c: newsprite`，191 行）：

```
newsprite(pack, id)
├─ sprite_size(pack,id)：算要多大内存
│    · picture 等叶子：sizeof(struct sprite)
│    · animation：sizeof(struct sprite) + (部件数-1) 个孩子指针
│      （struct sprite 末尾是柔性数组 children[1]）
├─ lua_newuserdata 申请这块内存（精灵本身就是 Lua userdata，随 Lua GC 回收）
├─ sprite_init：填 type/id/颜色/帧信息，孩子指针先全置 NULL
└─ 对 component 花名册里每个部件，递归 newsprite(子id)：
      ├─ sprite_mount(父, i, 子)：挂到 children[i]，回填 parent、name
      └─ 在 Lua 侧用一个 uservalue 表持有子节点引用（避免被 GC、也支持 obj.xxx）
```

要点：

- **模具 pack 用偏移量而不是指针**（`offset_t` + `OFFSET_TO_POINTER(pack, off) = pack基址 + off`）。因为资源可能从文件整块读入或重定位，用"相对偏移"最稳；实例 sprite 才用真正的指针。
- 实例树里，animation 节点的 `data.children[]` 指向子精灵；picture 等叶子没有孩子（这块内存被 union 复用为 rich_text / scissor / anchor）。
- `obj.turret` 的访问链：Lua `__index` → C 按名字 `sprite_child` 找到 component 下标 → 取出 `children[i]`（见 `ejoy2d/sprite.lua` 的 `fetch`）。

## 10. 颜色 / 加色 / shader 也会随层级继承

层级传递的不止矩阵，还有一个叫 `sprite_trans` 的包裹（spritepack.h:78）：

```c
struct sprite_trans { struct matrix *mat; uint32_t color; uint32_t additive; int program; };
```

每向下复合一层（`sprite_trans_mul_`，sprite.c:324）：

- 矩阵相乘；
- **颜色相乘**（`color_mul`，逐通道 /255）：父节点染成红色，整棵子树都偏红；
- **加色相加**（`color_add`，截断到 255）：发光叠加；
- shader：子节点没单独指定就继承父节点用的 program。

所以"父改颜色 / 换特效 shader，孩子跟着变"，和矩阵是同一套递归复合机制。

## 11. 一次 draw 的完整递归（和第一讲合拢）

```
Lua: obj:draw(screencoord)
 └ lsprite.c ldraw：把 {x=512,y=384,scale=1.2} 转成 srt
   └ sprite.c sprite_draw → draw_child(根, srt)
        │  当前是 animation：
        │   f = get_frame() 取当前帧
        │   对帧表里每个 part：
        │     ct = M_part × 父累积变换（局部在左，sprite_trans_mul2）
        │     递归 draw_child(孩子, ct)
        │
        └ 遇到 picture 叶子：switch_program(选shader) + shader_texture(选图)
             4 个角：
               vx = (screen_x·m0 + screen_y·m2)/1024 + m4   （局部→世界，定点）
               vy = (screen_x·m1 + screen_y·m3)/1024 + m5
               再 screen_trans 换算到 NDC（第一讲）
               UV 直接取 texture_coord
             shader_draw(4顶点, 颜色)  ── 攒进合批大数组（第一讲）
帧末 shader_flush：一次 glDrawElements 把整棵树可见的矩形全画出来
```

一句话把两讲连起来：

> **精灵树负责"算出每个矩形这一帧该在哪、用图的哪块、染什么色"（本讲）；合批器和 GPU 负责"把这些矩形高效变成像素"（第一讲）。**

## 13. 自测题与答案

**Q1. 同一个 "cannon" 调用两次 `ej.sprite`，得到几个精灵？哪些数据共享、哪些各自独立？**

答：得到两棵独立的实例精灵树。它们共享同一份模具 `sprite_pack`（图片坐标、帧表）和同一张 GPU 纹理；各自独立的是当前帧 `frame`、位置/缩放/旋转、颜色等运行时状态。

**Q2. picture 里的 `src` 和 `screen` 分别是什么坐标？**

答：`src` 是纹理图片上 4 个点的像素坐标（抠图区域，编译后变 UV）；`screen` 是矩形 4 个角在精灵本地坐标系里的位置，用内部单位（1/16 逻辑像素）。两组点一一对应完成贴图。

**Q3. 矩阵 `{1024,0,0,1024,0,800}` 和 `{-1024,0,0,1024,0,0}` 各表示什么？**

答：前者线性部分为单位、向 y 平移 800 个内部单位，即 800/16 = **50 个逻辑像素**；后者 m[0]=-1 表示水平镜像（x 翻转），常用于炮管左右朝向切换。

**Q4. 为什么 `turret.frame += 3` 只让炮管转、底座不动？**

答：`frame` 是每个动画实例各自的状态。根 cannon 只有 1 帧（恒静止），它提供整体变换；turret 是子动画，有几十帧并独立循环播放，帧表里变化的局部矩阵只作用于炮管这条分支。

**Q5. 子部件的世界矩阵怎么算？**

答：本引擎用**行向量** `p * m`，"先 A 后 B" 写成 `A * B`。递归每深入一层就把该部件当前帧的局部矩阵乘在父累积矩阵的**左边**，所以
`M_world = M_part × M_parent × … × M_root × M_srt`（局部在最左、最先作用，draw 传入的 SRT 在最右、最后作用）。叶子角点 `p * M_world` 得到世界坐标。注意这和列向量教材 `M_root×…×M_part×p` 是镜像写法，别套反。

**Q6. 帧表里每个 part 至少包含哪两样信息？**

答：`index`（用花名册里的哪个部件）和 `mat`（这一帧该部件相对父节点的局部矩阵）；还可能带 `touch`（是否可点）。
